# 반응형·접근성 Browser 검증 (#305)

2026-11-08, Windows / Codex 인앱 Chromium 브라우저, 기준 `develop` `45fa97d` (#304 병합).
물리 기기나 OS 배율 변경이 아닌 CSS Viewport 설정이다. 제품 코드·API·의존성·CI는 바꾸지 않았다.
승인 시안의 정보 구조와 조작을 비교했으며, 픽셀 일치나 최종 디자인 승인을 판정하지 않는다.

## 원본과 제품 비교

[재현 표](../../frontend/scripts/ui-audit/README.md#화면-비교-재현-305)에 따라
1440×1000 / 390×844(client 폭 1425 / 375), `scrollY=0`에서 원본과 제품을 각각
Viewport·Full-page로 캡처했다(핵심 비교 24장). 원본의 Studio 및 시연 행은 제외했다.
제품은 실제 React 라우트/스타일에 합성 응답을 연결한 것이며 실제 매물이나 운영 환경이 아니다.
브라우저가 반환한 첫 화면 JPEG는 원본/제품 모두 각각 1425×990 / 375×812였다.
이는 브라우저에서 측정한 CSS Viewport와 별개의 캡처 출력 크기다.

| 화면 | 일치하는 구조 | 남은 차이와 이유 |
| --- | --- | --- |
| Home | A1 전체 폭 Hero, 상단 Overlay, 내부 닫힌 검색, Navy & Ivory, 하단 사진 탐색 | 제품의 Scrim과 메뉴가 더 뚜렷하고 시안의 가상 기본 검색값을 채우지 않는다. 브랜드 AI 이미지와 실제 응답 Media를 구분한다. |
| Search | Desktop 필터 + 사진 카드 2열, Mobile 필터 Sheet + 카드 1열 | 시안은 가상 카드 4개, 제품 비교 Fixture는 ACTIVE 3개. 실제 API에 없는 요금 집계·리뷰는 표시하지 않는다. |
| Detail | 비대칭 Gallery/모바일 대표 사진, 하나의 객실 탐색, Desktop 예약 Rail/모바일 하단 CTA | 이미지 수·내용, 이용 안내의 길이와 Gallery 배치는 DTO/계약에 따라 다르다. 비어 있는 Room Metadata나 정책은 시안처럼 채우지 않는다. |

별도 화면은 [#271 구성안](../ui/prototype-rebuild.md)을 기준으로 Booking의 요약/예상가와 입력,
예약 상세의 저장 정보, Auth의 라벨과 로그인 행동, Admin의 대상/현재 값/편집 분리를 확인했다.
이 화면들은 전용 승인 원본과의 픽셀 비교 대상이 아니다. Search의 Loading/Empty/Error와
사진 있음/미제공/실패/부분 실패는 Audit Fixture에서 관찰했다. 부분 실패에서도 정상 사진과 카드가 유지됐다.

## 리플로우와 키보드

- 768×800에서 Search·Detail·예약 상세·Admin Calendar, 320×568 + root 글자 32px(200%)에서
  Home·Search·Detail·Login·예약 상세·Admin 가격/Calendar의 문서 가로 넘침이 없었다.
  320px 재고 표는 239/1152px, 저장 요금 표는 183/768px(보이는 폭/전체 폭)으로
  이름 있는 내부 영역에 한정됐다. 재고 표는 키보드 포커스와 오른쪽 화살표 스크롤을 확인했다.
- 390×568에서 메뉴·검색 필터·달력·숙소 Gallery·객실 Sheet를 키보드로 열었다.
  닫기 버튼에 포커스가 들어가고, Escape 후 트리거 및 body 스크롤 잠금이 복구됐다.
  메뉴에서 Tab은 홈 링크로 이동했다. 확인한 포커스는 3px Navy 외곽선이 표시됐다.
- 390×568 Detail에서 고정 CTA 상단은 y=499, CTA가 이동시킨 날짜 제목/다음 날짜 버튼의
  하단은 각각 약 y=54/148로 가리지 않았다. 320×480 + 글자 200% 달력은 Viewport 안에서
  내부 스크롤(높이 440px / 콘텐츠 2515px)을 제공하고 Escape로 복귀했다.
- 테마의 단색 대비 표본: 흰색/Navy 11.36:1, 본문/Ivory 12.05:1, 보조 글자/Ivory 5.17:1,
  오류 글자/배경 5.97:1, 입력 테두리/표면 3.89:1. 사진 위 글자 대비의 전 픽셀 검사나
  보조 기술을 통한 접근성 적합성 판정은 아니다.

## 실제 API·Media와 검증 경계

[격리 실행기](frontend-backend-integration.md)의 `--hold`로 실제 MySQL·Redis·Kafka와
전용 Media를 사용했다. API 스모크 및 브라우저 390×844의 Home·Search·Detail에서 업로드한
합성 이미지가 디코딩되고 `object-fit: cover`로 그려지는 것을 확인했다. Detail의 대표 사진은 eager,
객실 사진은 lazy였다. 세 경로의 관찰 구간에서 Console error는 없었다. 이는 전체 네트워크 요청
개수·중복 전송·캐시 적중률·성능 측정이 아니다. 브라우저 검수에서 실제 사용자 쓰기는 하지 않았고
실행기가 만든 프로젝트·볼륨·파일만 정리했다.

확인한 범위에서는 수정이 필요한 재현 결함을 찾지 않았다. 브라우저 자체 줌, 실기기 safe-area
및 가상 키보드, 스크린리더, Safari/Firefox, 장시간 네트워크 및 운영 Media는 미검증이다.
일회성 캡처는 Git에 포함하지 않으며, 최종 사용자 시각 승인과 종료는 별도 REVIEW 범위다.

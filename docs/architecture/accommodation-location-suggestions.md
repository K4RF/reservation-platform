# Accommodation Location Suggestions

## API 계약

`GET /api/v1/accommodations/locations/suggestions?q=서울`은 인증 없이 호출할 수 있습니다.
사용자 인증이 있는 경우에도 같은 후보를 반환합니다. 숙소 등록·수정 권한은 변경하지 않습니다.

- `ACTIVE` 숙소에 실제 저장된 `country`, `city`가 모두 있어야 도시 후보가 됩니다.
  지역 후보는 해당 숙소에 구조화된 `region`도 있어야 합니다. 상세 주소에서 이름이나 계층을 추정하지 않습니다.
- 도시 검색은 일치 도시와 그 도시의 실제 하위 지역을 대상으로 합니다. 지역 이름만 일치한다고
  부모 도시를 후보에 추가하지는 않습니다. 후보는 최대 10개입니다.
- 이는 공개 카탈로그에 위치가 존재한다는 의미입니다. 객실, 날짜별 재고, 요금 또는 예약 가능성을
  보장하지 않습니다. 날짜별 조건은 숙소 통합 검색에서 확인합니다.
- `q`의 앞뒤 유니코드 공백을 제거하고 연속 공백을 하나로 줄인 뒤 대소문자를 정규화합니다.
  누락·빈 입력·정리 후 유니코드 코드 포인트 2개 미만·일치 없음은 `200 []`입니다.
  원문이 100 Java 문자열 단위(UTF-16)를 초과하면 `400 COMMON_001` (`errors[].field=q`)입니다.
  `%`, `_`, `!`, `\`는 일반 문자입니다.

```json
[
  {
    "type": "CITY",
    "displayName": "서울특별시",
    "searchParams": { "country": "대한민국", "city": "서울특별시", "status": "ACTIVE" }
  },
  {
    "type": "REGION",
    "displayName": "강남구",
    "searchParams": { "country": "대한민국", "city": "서울특별시", "region": "강남구", "status": "ACTIVE" }
  }
]
```

선택한 후보의 `searchParams`를 [숙소 통합 검색](accommodation-integrated-search.md)에
그대로 전달합니다. 지역 선택은 정확한 국가·도시·지역의 활성 숙소만 찾고, `region`이
생략된 도시 선택은 해당 국가·도시 전체의 활성 숙소를 찾습니다. 지역의 `displayName`만으로
재검색하면 동명을 구분할 수 없습니다. 후보를 선택한 경우 입력했던 `q`를 `destination`으로
함께 보낼 필요가 없습니다. 도시 선택 시 이전 선택의 `region`도 남기지 않습니다.

## 매칭과 정렬

모든 토큰이 도시 후보의 `city`, 또는 동일 지역 후보의 `city`나 `region`에 부분 일치해야 합니다.
순위는 정규화된 전체 질의 기준으로 **정확 일치 → 접두 일치 → 부분 일치 → 토큰만 일치**입니다.
도시 후보의 비교 이름은 도시, 지역 후보의 비교 이름은 지역 및 `도시 지역`입니다.
동률이면 도시가 지역보다 먼저 오고, 이후 `country`, `city`, `region`, 숙소 ID 오름차순입니다.
예를 들어 `서울`이 `서울특별시`에 접두 일치하면 도시가 접두 일치한 하위 지역보다 먼저 옵니다.

도시는 `(country, city)`, 지역은 `(country, city, region)`으로 중복을 제거합니다.
비교·정렬·중복 판정은 MySQL 문자열 collation의 영향을 받으며, 중복 시 가장 작은 일치 숙소 ID의
저장 표기를 씁니다. 같은 도시명은 국가로, 같은 지역명은 국가와 부모 도시로 구분합니다.
같은 튜플에 저장된 서로 다른 실제 위치나 별칭은 현재 데이터만으로 구분·통합할 수 없습니다.
별도의 위치 마스터/ID, 별칭 사전, 외부 지도 연동 및 화면 연결은 이번 범위에 없습니다.

## 쿼리와 검증

입력이 짧거나 검증에 실패하면 후보 쿼리를 실행하지 않습니다. 유효한 입력은 한 번의 매개변수화된
`SELECT`로 처리합니다. 두 후보 분기에서 매칭한 후 DB 윈도 함수로 중복을 제거하고,
최종 정렬 후 `LIMIT 10`을 적용합니다. 숙소 엔티티 로딩, 후보별 재조회 또는 별도의 count는 없습니다.
부분 일치의 선행 `%`는 도시·지역 인덱스에서 범위 검색을 보장하지 않습니다. 결과 전송량은 제한하지만
DB의 후보 행 읽기·정렬 작업까지 10행으로 제한하지는 않습니다. 스키마·인덱스 변경은 없습니다.

격리 MySQL 테스트 `AccommodationLocationSuggestionIntegrationTest`는 실제 후보 SQL과 바인딩 값을
캡처해 JDBC 호출 1회와 DB 상한을 확인하고, 동일 쿼리에 대한 `EXPLAIN`을 테스트 로그에 남깁니다.
MySQL 8.4의 15개 지역 fixture에서 `q=District`를 조회한 결과, 도시/지역 분기 모두
`accommodations`에 `ALL`(선택 인덱스 없음)과 `Using where; Using filesort`가 나왔습니다.
최종 분기는 파생 결과에 `ref`(자동 생성 키 `<auto_key0>`)와 `Using filesort`를 사용했습니다.
이는 해당 fixture의 관찰 결과이며 운영 데이터의 인덱스 선택이나 지연 시간을 보장하지 않습니다.

# v0.5.0 HTTP 성능 및 회귀 보고서 (#349)

Reservation Platform의 격리 HTTP 실험을 종합한다. **이 결과는 단일 Backend·Broker의
비교 기준이며 운영 TPS, SLO, 포화점, HA 또는 Browser UX의 증거가 아니다.** 제품의
Outbox 기본 1초, 캐시 범위, 예약 락·트랜잭션, Consumer 원장은 그대로다.

- 격리 실행 16회, HTTP 3,020건: 200 2,753건, 201 264건, 예상 409 3건.
  drop·timeout·transport·비예상 오류·미확정 쓰기 0건. 사전 smoke와
  부하 외의 400/403/404/409 계약 검증은 이 수에 넣지 않았다.
- 16개 run에서 준비 이력 이후 커밋된 Outbox 570건과 소비 원장 570건을 대조했다.
  최종 PENDING·lag와 DB/가격/재고 불일치는 0이었다. 별도 Kafka source/DLT
  대조를 실행한 정상 생명주기·최종 여정에서는 DLT 0이었고 순서가 일치했다.

## 환경 고정과 재현

제품 기준은 `develop` `c7273f5b03ba47c4c9a4c92acaa43daf077e0173`(#348 병합)이다.
동일한 Boot JAR, MySQL·Redis·Kafka·Java·fixture·k6 이미지와 resource limit를
사용해 한 번에 한 실험만 실행한다. 로그인, 고정 시드와 단일 사용자 smoke,
초기 Outbox drain/캐시 준비, 사후 SQL·Kafka·정합성 검증은 HTTP 측정에서 제외한다.
유한 준비 구간이 JVM steady state를 보장하지는 않는다.

```powershell
Push-Location backend
.\gradlew.bat build
.\gradlew.bat test --rerun-tasks
Pop-Location
node --test load-test/*.test.mjs
node load-test/run.mjs prepare --confirm=isolated --seed=349 --stay=2026-12-30 --profile=final-mixed --cache=warm --room=distributed
node load-test/run.mjs run <run-id> --confirm=<run-id>
node load-test/run.mjs cleanup <run-id> --confirm=<run-id>
```

Gradle 테스트에는 Docker와 테스트용 Redis가 필요하다. 개발 Redis에 연결된
포트를 재사용하지 않는다. 별도 loopback 테스트 Redis라면 해당 셸에만
`SPRING_DATA_REDIS_HOST` / `SPRING_DATA_REDIS_PORT`를 지정할 수 있다.

위 날짜가 지나면 UTC 9~150일 범위의 미래 날짜를 고르고 비교 그룹에는 같은 날짜를 쓴다.

## 부하 모델과 판정

| Profile | 명목 제공 | 한 iteration |
| --- | --- | --- |
| read-heavy `final-read` | 1×6초 → 2×6초 → 3×12초, 2초 간격, 최대 VU 2/2/4 | 공개 검색→숙소 상세→가용 객실→객실 상세→일별 적용가, 5 GET. warm·distributed |
| write-heavy `lifecycle-write` | 기존 1×6초 → 2×6초 → 3×8초, 동일 간격, VU 1/2/3 | JWT 회원이 생성→일정 변경→취소, 3 HTTP. 캐시 off, VU별 객실 분산. #348의 1s/250ms 외에는 동일 |
| mixed `final-mixed` | read-heavy와 같은 도착률. warm·distributed 기준, warm·hot, cold·distributed 분리 | 5회마다 탐색 3번(각 5 GET), 예약 유지 1번(7 HTTP), 일정 변경·취소 1번(9 HTTP). 쓰기 여정은 방 검증과 POST 사이 100ms 대기, 생성 후 본인 상세 확인 |
| stability `final-stability` | 1×6초 → 2×6초 → **1×90초 유지**. 최대 VU 2/2/4, 실행기 145초 상한 | mixed와 같은 비율의 warm·distributed. 지속 운영/무한 soak가 아닌 유한 표본 |

mixed의 60/20/20, 100ms 및 체류 조건은 합성 가정이고 실서비스 분포가 아니다.
비율은 각 단계에서 처음부터 순회하므로 단계 끝에 따라 관측 비율을 따로 기록한다.
hot에서도 사용자/소유자는 VU별이고 **객실만** 같게 한다. warm과 cold 비교는
객실 선택을 동시에 바꾸지 않는다. cold는 소유 Redis의 상세 키만 비운 첫 순회로,
JVM·DB cold나 별도 인프라 장애를 뜻하지 않는다. 명시된 유지 구간 외부에서
VU/도착률/timeout을 임의로 높이지 않는다.

- [k6 도착률 모델](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)의
  iteration/s와 HTTP RPS를 분리한다. 전체 RPS는 최초~마지막 HTTP 완료 간격,
  제공/완료 수는 단계 창 기준이다. 종료 경계 추가 1회는 실제 완료에 표시하고,
  부족·drop·5xx·timeout·미확정 쓰기는 성공으로 집계하지 않는다.
- [k6 요청 지연](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)은 연결
  준비나 think time과 구분한다. `summary.json`에 단계·Endpoint·응답 코드/결과별
  n / p50 / p95 / p99, aggregate RPS와 drop/timeout을 보존한다. 서로 다른
  Endpoint나 성공/409의 p99를 한 숫자로 섞지 않는다.
- 읽기 조건의 성공은 전망치가 아니라 정확한 응답·변경 없는 재고/예약/이벤트로
  검증한다. 혼합은 확정 유지와 취소를 각각 계산하고, 기간별 재고/Version,
  첫 날짜·박별 가격·합계·취소 정책/수수료까지 저장값을 대조한다.
- Kafka의 Publisher 누적 발행/소비 원장은 cleanup 미구현으로 정상적으로 늘 수
  있다. `PENDING`/최고 age, partition lag, 사후 drain은 별도다. 최종 여정과
  write-heavy는 50초 drain budget을, 이전 독립 profile은 기존 제한 poll을 사용한다.
  성공 시 Outbox→소비 원장→Kafka key 및 파티션/offset을 맞춘다.
  `processed_at`은 Consumer DB commit 완료 시각이 아니다.
- `observations.jsonl`은 DB digest·row lock, Redis 정보·명령, JVM/GC·Hikari,
  컨테이너별 CPU/메모리와 처리 적체의 표본이다. Redis 전체 keyspace hit/miss와
  명령은 상세 Cache hit ratio가 아니다. 없어도 되는 표본 채널이 누락되면 표시한다.

원시/요약/검증 산출물과 seed/이미지/SHA는 기존과 같이
`.local/load-test/<run-id>/`에만 보존한다. [안전 규칙](../../load-test/README.md)을
따라 운영·개발 DB/Redis/Kafka·볼륨과 연결하지 않고, 쓰기 결과가 모호해도 재전송하지
않는다. 실패 run은 원장/로그를 먼저 확인하며 합성 자원만 명시적으로 정리한다.

인스턴스 공용 명령도 포함하므로 hit ratio가 아니다. 캐시별 단건 DB load 근거는

응답·경합이 항상 같다는 뜻은 아니다.

warm·분산 반복은 각각 57 여정·20 예약·40 이벤트로, 전체 12.32 RPS와
